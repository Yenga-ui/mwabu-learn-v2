## Data and security

Upgrade API and web together. Older binaries use strict document deserialization and must not be rolled back over newly saved schema-3 documents without a data-compatible plan. No additive database migration is necessary: existing JSON lesson snapshots store schema-3 documents. Historical migration files and EF snapshot are unchanged. Permission definitions/IDs/grants are unchanged. Schema-1/2 lesson documents still deserialize; omitted teaching steps on existing save/AI-apply paths preserve the saved preparation. Published lessons remain immutable; revise through the established duplicate/draft/review flow.

The classroom endpoint omits private fields entirely. Pinned asset ID/checksum pairs are checked on save/publication and resolved again using the published catalogue during playback. Unavailable versions fail visibly instead of following newer drafts or primary assets. Offline exports whitelist public fields and bundle only checked approved dependencies; they contain no session credentials, private step notes or learner records. Arbitrary HTML/scripts and generated code are never executed by the activity engine. Existing standalone practice and authenticated assessment marking remain unchanged.

## Performance and mobile findings

No new dependencies, background inference slots or mobile project were added. The final production build measured the teaching route at 5.30 kB raw / 2.09 kB gzip and preparation at 12.65 kB raw / 4.19 kB gzip, excluding shared chunks. These are bundle observations, not low-end Android or projection performance benchmarks. Existing 25 MiB package, 1 MiB range, 50 MiB cache and bounded activity constraints remain in place. The complete browser regression observed a 189 ms job acknowledgement with a deliberately eight-second inference fixture; it measures queue responsiveness, not real model speed or quality.

Recommend a hardware-tested Capacitor Android pilot for Sprint 4, reusing these public contracts and renderers with app-private verified package storage. Evaluate native display/media integration only where measured hardware requirements justify it. See mobile-app-readiness.md for the comparison and primary documentation references.

## Production acceptance and limitations

Implementation completion does not mean production classroom readiness. Physical Android/projector casting, landscape/fullscreen/audio, low-memory/thermal behavior, a 60-minute lesson, assistive technology, educator/local-language quality and operator export/device policy need documented acceptance. Viewport simulations cannot establish those hardware capabilities. Independent external displays are not implemented or universally promised. The website cannot initiate arbitrary hardware casting, force orientation or hide device notifications.

Timers, manipulation state and answer reveals are transient and reset on reload; the saved lesson revision remains pinned. Legacy planning prose is deliberately not projected until a teacher writes learner-facing content. Resource availability can change after preparation, and playback fails safely. Exports cannot enforce later revocation or encrypt themselves; they must be handled under approved school policy. Identifiable offline learner progress remains disabled. AI text outlines/storyboards are reviewable plans, not functional animation assets, and real provider content requires educator review before publication.
