# Operations and deployment

This branch implements the backend foundation; deployment approval requires the verification gates below. It does not claim production readiness from SQLite tests alone. Existing `/api` routes remain version 1; Swagger documents v1 and sync envelopes carry schemaVersion 1. Additive fields/routes are compatible changes. Breaking changes require a parallel explicit version and a documented client migration/deprecation window; do not rename current routes.

## Configuration and startup

Use `deployment/production.env.example` as a list of configuration names, not a secret file to commit. Supply PostgreSQL credentials, a random JWT signing key, encrypted Data Protection certificate/password and storage credentials through the deployment secret store. Production requires PostgreSQL `SslMode=VerifyFull` (install the correct CA/root certificate), explicit HTTPS browser origins and durable encrypted database Data Protection keys. There is no fallback connection or default administrator. Configure exact trusted proxy addresses only when TLS terminates at that proxy. Restrict the container HTTP port and health routes to the private network. Set AllowedHosts to the actual public hostnames at deployment.

Build: `docker build -f deployment/Dockerfile -t mwabu-learn-api:review .`. The runtime uses the .NET image's non-root APP_UID and port 8080. Mount only the writable local content/spool volumes required by the selected provider; mount PFX secrets read-only and readable by APP_UID. Use a read-only root filesystem with writable temporary/spool mounts when the host supports it. Terminate HTTPS at the trusted ingress; never publish the internal HTTP port to the Internet. Size spool storage for concurrent maximum uploads. Pin reviewed image digests in the release system and scan them regularly.

`docker compose -f deployment/compose.yaml up -d` provisions optional loopback PostgreSQL development infrastructure only, with an operator-supplied POSTGRES_PASSWORD. `compose.minio.yaml` is a separate optional HTTPS object-storage profile requiring MINIO_IMAGE, credentials and trusted certificates. MinIO's community repository is archived; do not assume historical image tags are maintained. Review the selected distribution/license/security support or use a supported S3 provider. No infrastructure command applies an application migration automatically.

## Migrations and recovery

Generate review SQL with `dotnet ef migrations script --idempotent --project backend/src/MwabuLearn.Infrastructure --startup-project backend/src/MwabuLearn.Api -- --offline`. Offline mode rejects database connections. For reviewed operator application, supply MWABU_MIGRATIONS_CONNECTION explicitly and use a separate migration-owner identity; runtime identities should not own schemas or be able to disable audit triggers. Apply during a controlled maintenance/deployment window and verify readiness before routing traffic. Inspect locks/table sizes and test on a restored copy first. Do not automatically retry writes around external storage or transactions.

Back up PostgreSQL (including Identity, refresh hashes, sync history/checkpoints and encrypted DataProtectionKeys), private objects/local files and encryption certificates/private keys through separate protected channels. Enable appropriate PostgreSQL PITR/WAL and object versioning policies. Document RPO/RTO and perform restore drills. A database backup without the Data Protection decryption certificates cannot recover cursors/reset tokens. Keep previous certificates configured through DataProtection:PreviousCertificates during rotation. Retain previous decryption certificates until every dependent key/token has expired or clients have been deliberately reset. JWT signing-key replacement currently invalidates all access tokens; plan a controlled reauthentication window (multi-key JWT rollover is deferred). Refresh/session state remains authoritative in PostgreSQL.

Restoring an older database may invalidate cursors whose version exceeds restored history: clients must restart bootstrap on 409. Do not delete sync history independently of a designed client-expiry/rebootstrap policy. Reconcile missing/orphaned objects against metadata/backups before deleting anything. Ambiguous S3 upload completion can leave an orphan; current compensation deliberately avoids deleting a possibly successful immutable object without authoritative metadata evidence.

## Health and incident response

GET `/health/live` and compatibility `/api/health` return a minimal process status. GET `/health/ready` checks database connectivity, unapplied migrations and configured storage with bounded cancellation; failed dependencies return generic 503. Health responses do not expose configuration, environment, credentials or exception text. Liveness does not require PostgreSQL; readiness does. Probe endpoints require network access control at ingress.

Investigate correlation/trace IDs, response status and fixed failure codes. For leaked user credentials use logout-all/deactivation; for leaked device proof revoke/rotate the device. Monitor failed/expired job leases and terminal failures; no automatic destructive retry beyond the configured maximum. Background work is at-least-once, with idempotent asset deletion, bounded claims, leases, cancellation and exponential retry. Operators may inspect failed jobs through controlled database tooling; there is no public generic job administration API. Graceful shutdown cancels work; leases recover after expiry. Never copy tokens, bodies, SQL parameter values or personal data into incident logs.

## Observability

JSON request logs contain correlation ID, route template, status, elapsed time and authenticated GUID user/device identifiers. Framework SQL/client diagnostic logs are suppressed to prevent raw SQL, URLs and provider errors; safe exception diagnostics record exception types. Do not enable EF sensitive-data logging, request-body/header logging or debug provider diagnostics in production.

Observability:Enabled defaults true; SampleRatio defaults 0.1. ActivitySources/Meters include MwabuLearn.Api, MwabuLearn.Backend and Npgsql with ASP.NET Core and outbound HttpClient instrumentation. Optional Observability:ExportOtlp=true requires an explicit HTTPS Observability:OtlpEndpoint (standard OTLP gRPC). Configure collector trust/access credentials privately; the SDK supports standard OTEL_EXPORTER_OTLP_HEADERS. No exporter/vendor is required. The trace processor whitelists operational dimensions, removes SQL/URL/query/baggage and status descriptions, normalizes span names and suppresses exception-payload spans before export. Metrics use framework operation/status dimensions and custom bounded route/job/stage dimensions. Verify collector privacy/access/retention before enabling export. Tracing is sampled, not an audit substitute.

## Verification gates

CI restores, builds Release with warnings as errors, runs every test including an isolated PostgreSQL database, rejects skipped tests, checks model drift/original migrations/dependency advisories, creates review SQL/bundle artifacts, builds the Linux image and smoke-tests non-root Production liveness/readiness. The PostgreSQL fixture creates and drops only a randomly named test database on an explicitly supplied loopback test server; it never migrates a developer or production application database.

Local PostgreSQL tests: enable MWABU_RUN_POSTGRES_TESTS=true and supply MWABU_POSTGRES_TEST_SERVER for a disposable loopback server using Database=postgres and a role allowed to create/drop its new test database, then run dotnet test. Do not point this at a shared/production server. Without explicit enablement these five tests visibly skip. Docker and PostgreSQL execution were unavailable in the current local environment; CI execution and live S3 compatibility remain release gates, not inferred successes.
