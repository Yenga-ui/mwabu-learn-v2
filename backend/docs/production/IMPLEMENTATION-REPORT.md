2. **Baseline discovered.** Existing modular Domain/Application/Infrastructure/API backend on .NET 10, PostgreSQL/EF Core, ASP.NET Core Identity/JWT, organisation-scoped business roles, global catalogue authorization, curriculum/content/storage modules. Baseline restore/build succeeded and all 145 tests passed. Four existing migrations were preserved. Findings and phase evidence are in PROGRESS.md.
3. **Architecture changes.** Added focused Application contracts and Infrastructure services for sessions, auditing, devices, directories and sync. Controllers stay thin and use services; no new architectural framework, MediatR, AutoMapper, CQRS, microservices or generic ingestion. Shared DbContext coordinates atomic audit/feed/job records. Existing /api contracts remain v1 with additive routes; large legacy reads now fail safely rather than allocate without bounds.
4. **Authentication/session implementation.** Cryptographically random refresh credentials are persisted as SHA-256 hashes with family, expiry/absolute expiry, revocation/replacement and concurrency state. Serializable rotation permits one replacement; reuse commits family revocation before generic failure. Logout revokes its family; logout-all increments user access-token version and revokes every family. JWT validation checks active current user/version/lockout and session family. Existing short-lived pre-feature JWTs lacking sid remain accepted until expiry or account-version invalidation.
5. **Password lifecycle.** Identity owns password hashing, validators, stamps and reset-token providers. Authenticated change and successful reset invalidate sessions/access tokens. Forgot/reset use a real-delivery abstraction; the default explicitly returns 503 uniformly until an actual notification adapter is configured. No fake SMTP, token-in-response or delivery logs. A future adapter must durably accept delivery and preserve account-enumeration resistance on transport failures.
6. **Security hardening.** Strict startup JWT validation, explicit HTTPS production CORS origins, trusted proxy allowlist, HSTS, no-referrer/nosniff/frame protection, no-store auth/device credential responses, bounded auth bodies and account/IP/per-user/endpoint/concurrency limits. Generic ProblemDetails and fixed failure codes avoid secret/provider details. Production PostgreSQL requires VerifyFull and disabled error details. Durable Data Protection keys require an operator-mounted valid RSA encryption certificate and secret password. Bootstrap remains explicitly enabled, secret-supplied, strict and idempotent; no automatic administrator or migration.
7. **Audit implementation.** Identifier-only append-only records contain event/time/actor/org/entity/correlation, never profile snapshots or credential values. Business writes and their audit/feed records share a transaction. Explicit codes cover authentication, publication, role assignments, deactivation and devices. PostgreSQL adds an UPDATE/DELETE rejection trigger; application guards also prevent mutation. Platform users.read governs bounded audit search. No destructive retention job.
8. **Database changes.** Added refresh sessions, audit events, background jobs, devices, sync clock/change history/checkpoints and standard EF DataProtectionKeys. Explicit lengths, indexes, uniqueness, restrictive references and concurrency controls. Command/connect/pool bounds configured. No transparent write replay around external storage. Snapshot reads bound curriculum hierarchy consistently. The model drift check passed and idempotent SQL generated offline; no PostgreSQL migration applied.
9. **New migrations.** Six additive migrations, listed below; original four and their designers remain unchanged.
10. **Content storage implementation.** Maintained AWS SDK S3 provider with standard credential chain and HTTPS compatible endpoints. Observed-byte bounded private disk spool, SHA-256, immutable conditional puts, cancellation cleanup, idempotent deletes, seekable remote byte-range streams and safe readiness. Local provider retained. No public bucket URLs or credentials in sync. Ambiguous completed uploads may require orphan reconciliation; do not delete a possibly valid object speculatively.
11. **Background processing.** Durable asset-delete jobs created atomically with pending metadata. Bounded batches, atomic leases, expiry recovery, retry/backoff/max attempts, fixed safe error codes and graceful cancellation. Processing is at-least-once; deletion is idempotent. Terminal failures require operator review. Tests cover shutdown followed by lease recovery without losing metadata.
12. **Device registration.** First-class GUID/org/owner/client-registration/platform/version/UTC state; idempotent registration does not replay a credential. Independent random proof is hashed, expires, rotates and revokes. A device ID alone is insufficient. Active user, active membership, active organisation and content.read remain required; even a platform administrator needs membership for actual device use.
13. **Sync protocol.** Authenticated user plus registered active device receives only global curriculum and published catalogue metadata. Bootstrap and changes expose schemaVersion 1 and bounded envelopes, replayable GUID/type upserts and tombstones. Draft/in-review metadata and personal/Identity graphs are excluded. Microservers use the same read-only protocol; there are no arbitrary upstream writes or invented future domain conflict semantics.
14. **Cursor/checkpoint strategy.** Encrypted/authenticated purpose-specific Data Protection cursors bind user/device/organisation, stage, position/head window and expiry. PostgreSQL singleton clock row lock is held until commit, avoiding sequence allocation/commit-order gaps. Bootstrap overlaps a captured clock with subsequent replay to converge despite concurrent changes. Per-user/device monotonic checkpoints resume using protected cursors. Clients commit applied changes and cursor atomically; restore/history mismatch requests rebootstrap. No feed compaction implemented.
15. **Manifest/download strategy.** Bounded published/downloadable asset manifests filter by language/type/collection/grade/subject and return safe metadata, size, SHA-256 and authenticated API download URL. ETag, Range, If-Range, 206/416 and checksum permit integrity verification and resumed downloads. Archived content is denied by sync download. No ZIP packaging service was invented; the manifest is the package contract.
16. **Health/readiness.** /health/live and compatibility /api/health are minimal public process probes. /health/ready checks database connectivity/pending schema and configured storage with bounded cancellation; generic 503 on unavailable dependencies. Protect probes/internal HTTP at ingress. No environment or connection detail disclosed.
17. **Logging/observability.** Structured JSON logs with safe correlation, route template/status/duration and validated GUID user/device. Framework SQL/client diagnostics suppressed; no token/body/header/query logging. OpenTelemetry ASP.NET Core/outbound HTTP/Npgsql and custom sync/job tracing/metrics with sampling and optional HTTPS OTLP. Privacy processor strips URL/SQL/baggage/status descriptions, normalizes span names and prevents exception-payload spans from export. Collector access/retention must be approved operationally.

## Explicit security answers

| Question | Answer |
| --- | --- |
| Are raw refresh tokens stored anywhere? | Not in server persistence/logs. Only hashes are stored; raw values exist transiently for issuance and are returned once for client secure storage. |
| Can a revoked refresh token be reused? | No. Reuse fails and revokes its family; a lost rotation response requires login again. |
| Does logout invalidate its session? | Yes, its whole family and its session-bound access tokens. |
| Does logout-all invalidate existing sessions/access tokens? | Yes, all families plus user token version/security stamp. |
| Does password change invalidate other sessions? | Yes; current session also requires reauthentication. Successful reset does likewise. |
| Can Production run with AllowAnyOrigin? | No; invalid/empty/wildcard production origins fail startup. |
| Can Production start with weak/missing JWT key? | No; validated secret configuration is required. |
| Are migrations automatically applied at startup? | No. |
| Can an inactive user authenticate? | No; login/refresh/access-token validation deny them. |
| Can a revoked device sync? | No; active proof/state/context is checked each request. |
| Can an organisation user mutate the global catalogue? | Not through organisation-only grants; global management requires platform authority/permission. |
| Can content.manage publish without content.publish? | No; separate publication authorization remains enforced. |
| Can a client resume an interrupted asset download? | Yes, HTTP Range/If-Range with immutable asset ETag. |
| Can a client verify downloaded content integrity? | Yes, manifest SHA-256 and byte length; client must verify complete bytes. |
| Can sync resume from a checkpoint? | Yes, a protected user/device-bound monotonic checkpoint; expired/restored history may require bootstrap. |
| Are sync batches bounded? | Yes, <=100 records and configured byte budget, with bounded row/transaction limits. |
| Are sync operations retry-safe? | Read/replay/upsert/tombstone/checkpoint semantics are idempotent. Bootstrap/manifest may reflect concurrent publication; clients apply transactionally and replay. Refresh rotation intentionally is not replayable after reuse. |
| Does API expose secrets in logs/errors? | Implemented responses/logs/trace exports avoid tokens, PII fields, raw queries/SQL/provider messages; reviewed deployment diagnostics must preserve that policy. |
| Are health endpoints available? | Yes, liveness and bounded readiness; ingress must restrict probes. |
| Can API run in a Linux container? | Linux non-root build/runtime definitions provided; actual container execution not verified locally. |
| Does CI build/test the solution? | Workflow implements both including PostgreSQL and Docker gates; no successful remote run confirmed at handover. |
| Were any existing migrations modified? | No; only new migrations and the current model snapshot changed. |

## Added API routes

Existing catalogue/identity/organisation routes remain. Session additions: POST /api/auth/refresh, /logout, /logout-all, /change-password, /forgot-password, /reset-password. Existing login adds optional refresh/session timing fields; GET /api/auth/me remains protected.

GET /api/audit-events (platform users.read). Devices: POST/GET /api/organisations/{organisationId}/devices; GET /api/organisations/{organisationId}/devices/{deviceId}; POST that device's /credential and /revoke; GET /api/devices/current. Sync: GET /api/sync/bootstrap, /changes, /manifest, /checkpoint, /assets/{assetId}; PUT /api/sync/checkpoint. All sync routes require JWT, X-Device-Id and X-Device-Credential plus active context and catalogue permission.

Bounded directories: GET /api/curricula/search; /api/curricula/{id}/nodes/{type}; /api/organisations/search; /api/organisations/{organisationId}/members/search; /api/collections/search; /api/tags/search; /api/auth/me/memberships/search. Existing bounded content/user search remains. Health: GET /health/live, /health/ready and compatibility /api/health. Swagger remains available in Development with bearer authentication.
