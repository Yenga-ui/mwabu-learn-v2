# Catalogue sync protocol v1

All `/api/sync` endpoints require HTTPS, user bearer authentication, active registered-device proof (`X-Device-Id`, `X-Device-Credential`), active membership in the device organisation, organisation `content.read`, and an active catalogue grant for `curriculum.read`. Client organisation context must match the validated device. No arbitrary upstream JSON or future product records are accepted.

1. GET `/api/sync/bootstrap?pageSize=100` starts a bounded snapshot walk. Follow `nextCursor` on the same endpoint until `bootstrapComplete=true`. Each item has `entityType`, stable GUID `id`, `isDeleted`, and an explicitly projected `data` object. Schema version is 1. A batch contains at most 100 items and a configured bounded payload budget.
2. Apply each batch to local SQLite and persist its cursor atomically. Treat `(entityType,id)` as an upsert key. Retry the exact cursor if a response/application transaction fails. Apply parent node deactivation and content tombstones to visibility of descendants/associations/assets; do not assume server cascades physically delete them.
3. GET `/api/sync/changes?cursor=...&pageSize=100` replays changes since bootstrap's starting watermark, including changes overlapping snapshot pagination. Follow while `hasMore=true`; poll the returned cursor later when false. Bootstrap is a convergent current-state walk, not a frozen point-in-time snapshot. Overlap is intentional; idempotent upserts plus replay prevent missing insertions that sort before a snapshot cursor.
4. PUT `/api/sync/checkpoint` with `{ "cursor": "last-committed-nextCursor" }` acknowledges durable local application. Checkpoints are per user/device/catalogue scope, idempotent and monotonic. GET `/api/sync/checkpoint` returns the last position and a fresh protected resume cursor. Different users/devices cannot overwrite each other's checkpoint.

Cursor contents are integrity/confidentiality protected by ASP.NET Data Protection and bound to schema, user, device, organisation, stage and expiry. Tampering is 400, cross-context use 403, expiry/schema/history regression 409 with bootstrap restart. Never edit a cursor or derive it from timestamps/IDs. Do not put cursor/query values in logs. `Sync:CursorDays` defaults to 30; `MaximumBatchBytes` to 2 MiB (maximum 4 MiB). Keep feed history for at least the maximum accepted cursor lifetime plus an operating margin; no destructive feed purge is implemented.

A singleton transactional clock allocates one version per catalogue SaveChanges. Its row lock is held until commit, so committed version order cannot skip a late-committing allocation. Each version has deterministic ordinals. Change snapshots are written atomically with business metadata/audit. Rollback also rolls back the clock. This deliberately serializes catalogue writes, suitable for a modest editorial workload; measure lock contention before scaling writers. A raw PostgreSQL sequence/identity alone would be unsafe for this cursor guarantee. SQLite rollback/overlap tests pass; concurrent PostgreSQL verification is supplied separately and must run before release.

Bootstrap reads the existing migrated catalogue directly, so pre-feature records need no destructive rewrite/backfill. The feed starts at version 0 and captures subsequent API SaveChanges. Direct SQL/bulk updates to catalogue tables bypass change capture and are unsupported without a coordinated feed writer. Synchronous catalogue SaveChanges is rejected; production services use async SaveChanges.

Eight curriculum node types retain parent GUIDs and configurable metadata. Content snapshots contain only Published resources. Publication captures existing assets, collection/tag associations and curriculum mappings in bounded queries. Draft and InReview content/asset/mapping metadata never enters the downstream feed. Archiving produces a content tombstone. Active reference taxonomies are independent metadata; an unused taxonomy is not a draft content item. Current bootstrap may include inactive taxonomy/node tombstones. No media bytes are embedded in metadata batches.

GET `/api/sync/manifest` returns bounded published/downloadable asset metadata. Filters: languageCode, contentType, gradeId, subjectId and collectionId; grade/subject filters include explicit descendant mappings. Each entry has SHA-256, observed byte length, media type and an API download route. Storage keys/credentials are omitted. Offset manifest pages describe current availability; use bootstrap/change cursors for durable metadata synchronization and recheck a manifest when publication changes.

GET `/api/sync/assets/{id}` requires the same user/device authorization. Only currently published downloadable assets are available; archive immediately removes access. HTTP Range/If-Range supports resume with strong SHA-256 ETags and 206/416 semantics. Verify final byte length and SHA-256 before replacing a local asset. Partial files/cursors belong in a client-local transaction/recovery design, not in server memory. No compressed package builder or arbitrary object URL is introduced.

The protocol uses stable server GUIDs, opaque cursors, explicit schema version, UTC server time and idempotent batches so a future microserver can cache/relay it. A microserver implementation and upstream product-specific ingestion are deferred; any future upstream module must define typed ownership, operation IDs, validation/conflicts and duplicate handling rather than exposing generic table writes.

# Durable protection and deployment settings

Production requires `DataProtection:PersistKeysInDatabase=true`, a mounted RSA PFX encryption certificate, and `DataProtection:Certificate:Path`/`Password` from deployment secrets. The certificate must have a private key, at least 2048-bit RSA, current validity, and a secret password of at least 16 characters. The shared application discriminator is `MwabuLearn.Api.v1`. The standard DataProtectionKeys table stores encrypted key XML; no keys/certificates/passwords are committed.

Keep the key-ring database and certificate private keys in tested backups. All replicas need the same active/previous certificates. For rotation, mount the new active certificate and retain old certificates under `DataProtection:PreviousCertificates:{index}:Path`/`Password` until all tokens/cursors protected by them expire. Old certificates may be expired for decryption, but the active certificate must be valid. A local test proves an independent provider can decrypt persisted encrypted keys; actual deployment restore/rotation remains an operator rehearsal.

`Traffic` defaults: AuthIpPerMinute=1000, ApiPerUserPerMinute=600, SearchPerMinute=120, UploadPerMinute=20, SyncPerMinute=120, CredentialChangesPerMinute=10, ConcurrentDownloadsPerUser=4. Tune against measured school NAT/client workloads. Auth partition limits remain `Authentication:LoginAttemptsPerMinute` (default 10). Per-user policies avoid grouping authenticated users under a single school IP. Limits are local to each API process; a distributed ingress limit is required when scaling replicas.
